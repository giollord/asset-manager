## Requirements

### Requirement: Single-file catalog database
The system SHALL store all catalog data in exactly one database file: assets, files, sources, tags, collections, licenses, previews, embeddings and settings that belong to the catalog. The user SHALL be able to choose the file location. Copying that single file to another machine SHALL carry the entire catalog, including previews.

#### Scenario: Catalog is self-contained
- **WHEN** the user closes the app and copies only the catalog file to another location and opens it from there
- **THEN** all assets, metadata, tags, collections, licenses and previews are shown as before

#### Scenario: No side-car data folders
- **WHEN** assets with previews have been imported
- **THEN** no preview or metadata files exist outside the catalog file (excluding transient temp/cache files and AI model weights)

### Requirement: Asset model
An asset SHALL be a logical catalog entry of one type: 3D model, animation, image, texture, sprite sheet, audio, music, font, video, material, document or other. An animation is a motion clip stored in a model file; the stand-in character that often comes with it does not make it a model. It SHALL consist of one primary file and zero or more companion files, such as a model's textures. An asset SHALL belong to exactly one import source.

#### Scenario: Model with textures is one asset
- **WHEN** a model file is imported together with the texture files its materials reference
- **THEN** one asset of type 3D model is created whose primary file is the model and whose companion files are the textures

#### Scenario: Standalone texture remains its own asset
- **WHEN** a texture is not referenced by any imported model
- **THEN** it is cataloged as its own asset of type texture or image

### Requirement: Asset metadata
Each asset SHALL store:
- name
- type
- original file name(s) and format
- file size(s)
- provenance location
- description
- tags
- dominant color palette
- style descriptors
- the import date

Each asset SHALL also store type-specific technical metadata, as listed in the scenarios below.

#### Scenario: Image metadata
- **WHEN** an image or texture asset is imported
- **THEN** its pixel width, height, alpha presence, format and dominant colors are stored

#### Scenario: Audio metadata
- **WHEN** an audio asset is imported
- **THEN** its duration, sample rate, channel count, codec and bitrate are stored

#### Scenario: 3D model metadata
- **WHEN** a 3D model asset is imported
- **THEN** its vertex/triangle counts, mesh count, material count, bounding size, presence of skeleton and animation names are stored
- **AND** its real-world size, unit scale, root scale, any scale anomaly flag, source up-axis and applied orientation correction (with who decided it) are stored

### Requirement: Tags
Tags SHALL be case-insensitive, unique by normalized name and stored in English. An asset SHALL be able to have any number of tags. The user SHALL be able to add and remove tags on one or many selected assets at once. Each tag on an asset SHALL record its origin: user, import-wide, AI or source.

#### Scenario: Bulk tag add
- **WHEN** the user selects 50 assets and adds tag "medieval"
- **THEN** all 50 assets carry the tag "medieval" and assets already carrying it are unchanged

#### Scenario: Case-insensitive tag identity
- **WHEN** the user adds the tag "Sci-Fi" and the tag "sci-fi" already exists
- **THEN** the existing tag is reused and no duplicate tag is created

### Requirement: Tag-based collections
A collection SHALL be a named grouping defined by a tag rule: a set of tags that must all be present, plus optional excluded tags. An asset SHALL belong to every collection whose rule it satisfies, so one asset MAY be in several collections. Membership SHALL update automatically when tags change. A collection SHALL have a description, which can be written by the user or generated by the AI.

#### Scenario: Asset in multiple collections
- **WHEN** collection A requires tag "forest" and collection B requires tag "lowpoly", and an asset has both tags
- **THEN** the asset appears in both collections

#### Scenario: Membership follows tags
- **WHEN** a tag required by a collection is removed from an asset
- **THEN** the asset no longer appears in that collection

### Requirement: Source records
Each import source SHALL be recorded with:
- its kind: file, folder, archive or Unity package
- its original location
- its display name
- a content fingerprint
- package metadata when available: the Asset Store id, title, publisher, version and store URL
- notes, such as which scripts were present but not imported
- a link to the source it was nested in, if any

#### Scenario: Unity package provenance
- **WHEN** assets are imported from a `.unitypackage`
- **THEN** each asset references the package source, and the source shows the package file path and any Asset Store link found in the package

### Requirement: License and link information
The system SHALL record license information for a source and for individual assets:
- the license name or kind
- whether commercial use is allowed (yes, no or unknown)
- whether attribution is required (yes, no or unknown)
- the attribution text
- the evidence document it was derived from

The system SHALL also record related URLs. An asset SHALL inherit its source's license and links unless they are overridden on the asset.

#### Scenario: Inherited license
- **WHEN** a source has a license with "commercial use: allowed, attribution: required"
- **THEN** every asset from that source shows that license unless it has its own override

#### Scenario: Unknown license
- **WHEN** no license document is found for a source
- **THEN** commercial use and attribution are shown as "unknown"

### Requirement: Manual metadata editing
The user SHALL be able to edit an asset's or source's name, description, tags, license fields and URLs. Values edited by the user SHALL NOT be overwritten by later AI enrichment unless the user explicitly asks for regeneration.

#### Scenario: User edit preserved
- **WHEN** the user edits an asset description and later re-runs AI enrichment on it without choosing to overwrite
- **THEN** the user-edited description is kept

### Requirement: Bulk delete
The user SHALL be able to delete a selected set of assets, or entire sources, from the catalog after a confirmation that states how many assets will be removed. Deletion SHALL remove the assets' previews, embeddings, stored original copies and tag links. It SHALL NOT modify or delete any original files on disk.

#### Scenario: Delete selected assets
- **WHEN** the user selects 12 assets, chooses Delete and confirms
- **THEN** those 12 assets and their previews are removed from the catalog and the original files remain untouched

#### Scenario: Delete requires confirmation
- **WHEN** the user chooses Delete and cancels the confirmation
- **THEN** nothing is removed

### Requirement: Source tags
A source SHALL be able to carry source tags, each added by the user or by the AI. Every asset of the source SHALL carry each source tag with origin "source", including assets added to the source later by rescan, re-import or a new version. Source tags SHALL work in search, collections and counts exactly like asset tags. The Sources page SHALL show each source's source tags and let the user add and remove them.

#### Scenario: Tag the whole pack
- **WHEN** the user adds the source tag "pixel art" to a source with 240 assets
- **THEN** all 240 assets carry "pixel art" with origin "source", and a collection requiring "pixel art" includes them

#### Scenario: New assets inherit
- **WHEN** a source has the source tag "low poly" and a rescan imports 10 new assets into it
- **THEN** the 10 new assets carry "low poly"

### Requirement: Removing source tags
Removing a source tag SHALL remove it from the source's assets where its origin is "source". Copies of the same tag that the asset got from the user, the import or the AI SHALL be kept.

#### Scenario: Remove source tag keeps user copy
- **WHEN** the source tag "medieval" is removed and one asset also had "medieval" added by the user
- **THEN** that asset keeps "medieval", and the others lose it

### Requirement: Per-asset opt-out of a source tag
Removing a source tag from a single asset SHALL affect only that asset. The tag SHALL stay removed from that asset, also after later AI runs, re-imports and source updates.

#### Scenario: Opt-out survives re-import
- **WHEN** the user removes the source tag "pixel art" from one HD splash image and later re-imports the source
- **THEN** that image still does not carry "pixel art", and the other assets do

### Requirement: Favourites, ratings and notes
Each asset SHALL have a favourite flag, a rating from 0 (unrated) to 5 stars, and free-text notes. The user SHALL be able to set them on one asset in its details, and set the favourite flag and the rating on many selected assets at once. These fields belong to the user: AI enrichment, re-import and source updates SHALL never change them. The notes SHALL be included in full-text search.

#### Scenario: Rating survives re-import
- **WHEN** an asset rated 4 stars with the note "use for level 2 rocks" is re-imported with AI enrichment
- **THEN** it still has 4 stars and the same note

#### Scenario: Bulk favourite
- **WHEN** the user selects 20 assets and marks them as favourites
- **THEN** all 20 are favourites
